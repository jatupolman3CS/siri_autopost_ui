# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

The frontend for AutoPost, a SaaS that posts to Facebook groups and pages through browser extensions (Facebook is the only platform for now; the others are a later phase). The repo holds two apps:

- **Root:** an Angular 22 app (standalone, zoneless, signals, SCSS, Vitest) that implements the "AutoPost Dashboard" design from a Claude Design handoff. It covers the landing page, login/signup, the workspace screens (overview, the collection → link set → schedule flow, calendar, library, reports, test post, anti-ban, notifications, auto-reply, offline, errors, billing, team), the public client report (`/report/:token`) and 7 platform-admin screens.
- **`legacy/`:** the old Vite-hosted copy of the extension's dashboard, which talks to the legacy server `backend/SIRI.AUTOPOST.Server` in `siri_autopost_backend`. See "Legacy app" below.

User-facing text comes from the TH/EN dictionary, never from literals in templates (toast and error fallbacks in `core/http` are the only exception). Strings the design handoff lacks go in `core/i18n/i18n.extra.ts` (`t().api.*`), not in the generated `i18n.data.ts`. Copy of the design that contradicts what the system does is corrected in `core/i18n/i18n.fixes.ts`, never in the generated file (see "i18n"). Code comments are in English.

## Commands (Angular app)

```bash
npm install
npm start                 # ng serve on :4200 (proxy.conf.json sends /api to SIRIAUTOPOST.Api on http://localhost:5100; start it first)
npx ng test --watch=false # unit tests, single run (npm test = watch mode)
npx ng test --watch=false --include src/app/core/data/posts.store.spec.ts   # one spec
npm run build             # production build -> dist/siri-autopost-ui/browser
npm run format            # prettier (the only formatter; no ESLint)
npx prettier --check .    # the whole repo; .prettierignore skips legacy/, the extension libs, the API snapshot and prose
npm run import:design -- <autopost-data.js>   # regenerate i18n.data.ts + seed.data.ts from a design handoff
npm run gen:api           # openapi.snapshot.json -> src/app/core/http/api-schema.ts (prettier-formatted)
docker build -t siriautopost-web .   # nginx image: dist + /api proxy to http://api:8080 (nginx.conf)
```

The whole stack (PostgreSQL + API + this app) runs with `docker-compose.saas.yml` in `siri_autopost_backend`, which builds this repo from `UI_PATH` (default `../siri_autopost_ui`).

Angular CLI 22 needs Node ≥ 22.22.3 (or ≥ 24.15).

CI (`.github/workflows/ci.yml`) runs `prettier --check`, checks that `npm run gen:api` leaves `api-schema.ts` unchanged (commit the regenerated file with the snapshot), builds, runs the unit tests, builds `legacy/` and the Docker image.

## Architecture (Angular app)

- **Data comes from `SIRIAUTOPOST.Api`** (backend repo). `core/http/api.service.ts` is the only place that calls `HttpClient`: typed methods (types from `api-schema.ts`) that return promises. `core/data/*.store.ts` are `providedIn: 'root'` signal stores on top of it; pages read their signals and await their methods. Every store loader runs through `loadWithRetry` (`core/data/loading.ts`): a server that is down or busy (0, 408, 429, 5xx) is asked again after 2, 5 and 15 s, a refusal (4xx) is not, it never rejects, and an answer for a workspace or user that has gone meanwhile is dropped. The stores that load data have a `loaded` flag the pages read, so a page shows "—" rather than 0 or 100% before its data has arrived. Stores empty themselves when the workspace or the user changes (settings, draft, offline timestamp, admin data), so one workspace's values are never saved into another.
- **Auth.** `SessionStore` logs in/signs up against `/api/auth`, keeps the JWT in localStorage (`ap-token`, `core/auth/token.ts`) and checks it with `/api/auth/me` in `provideAppInitializer` before the first navigation. `restore()` drops the token only on a 401 (a server that cannot answer keeps it and sets `restoreFailed`, which the login page says). `authInterceptor` adds the bearer header and sends the user to `/login` on a 401; `signedInGuard` and the interceptor pass the wanted address as `?returnUrl=` and `AuthPageComponent` goes back there after signing in (`safeReturnUrl`: pages of the app only). `errorInterceptor` toasts failures except 401s and requests sent with the `QUIET` context (login, signup, uploads, background refreshes), whose callers show their own errors; a 400 toasts its first field message (else its title), and `NotificationService` does not stack an identical toast. The role (`user`/`admin`) and plan come from the server.
- **Workspaces.** `WorkspaceStore` loads the user's workspaces after sign-in and remembers the current one (`ap-ws`). Each workspace carries the *owner's* effective `limits` (plan plus the platform admin's overrides: accounts, posts per 24 h, devices, seats; null = unlimited) and `advancedAntiBan`, whatever plan the signed-in member has; the list is read again when the user's plan changes. Workspace-scoped stores call `whenWorkspaceChanges()` in their constructor to reset and reload when it changes (and to empty themselves on sign-out). Limits shown anywhere (team seats and devices, the anti-ban lock) come from there or from `GET /api/billing`, never from `plans()[session.plan()]`.
- **Permissions.** `PermissionsService` is the one place that decides what the signed-in person may do in the current workspace, from its role (viewer < editor < admin < owner) and assist mode (read-only for everything): `canEdit` (posts, library, reconnect, skip waiting and extension commands), `canAdmin` (anti-ban and offline settings, the offline simulation, devices, members), `readOnly`, `canCreateWorkspace` and the hint texts (`editHint`/`adminHint`). Every control the API would answer with a 403 binds `[disabled]` to it, with a `title` hint, and `<app-perm-note level="edit|admin">` says why under the page title. A viewer must never be able to click something that is certain to fail.
- **Stores.**
  - `PostsStore` loads posts a calendar month at a time (`ensureMonth`, which rejects when the API does; the months around today on load, the calendar asks for the rest) plus the open error reports, and `refresh()` re-reads both after every change and never throws. `loaded` is set once the first months and the errors are in. `items`/`byDay`/`today` add a day key and HH:MM (the local day); `postRow()` builds a list row. `now` is a signal that ticks every 30 s.
  - `AccountsStore` holds the accounts the extensions created (health, `connected`); `reconnect()` marks one signed in again. A new workspace has NONE (the sample accounts and the other platforms were removed on 2026-10-06; `PlatformKey` is just `'fb'`). `accountKind()` (models.ts) tells a `connected` account (a browser posts for it) from an `unbound` one (its browser was revoked: the API names it "Facebook · <browser>", it keeps its history and cannot post); `AccountsStore.connected` and `extensionNameOf(account, devices)` name the extension that posts a link set. The list follows the event stream (`device.groups`/`updated`/`paired`/`revoked` and `post` events, a re-read on every reconnect of the stream, a 60 s poll only while the stream is down).
  - `SettingsStore` holds the anti-ban and offline settings from `/engine` (edited locally, sent by `saveAb()`/`saveOff()`, which do nothing before `loaded`), the extension's presence (`extensionOnline`, `simulatedOffline`, `devices`, `devicesOnline`), and `used24h`: the Facebook posts that went out in the last 24 hours on connected accounts, success and awaiting approval (a number), which is what the server counts against the daily limit. Every minute it refreshes only the presence (quietly, so edits in progress survive) and, when a device is paired, the posts; in between, `device.online`/`device.paired`/`device.revoked` events refresh the presence and `post` events refresh the posts at once. Billing preferences stay local. `ab.advanced` carries the workspace-wide rules (min gap, overall daily cap, block pause hours, failure streak, recent avoid, cooldown, auto-off fails, stop at failure %, focus window; `patchAdvanced()`): the server enforces them and the auto-pause and warm-up switches (Pro and above; below it the stored values stay and the inputs are disabled), while the focus window and the rest after a Facebook block (`blockMin`/`blockMax`) are applied by the extension in the browser (the anti-ban page says so); shuffle is the order of the groups inside a schedule slot, which the schedule engine applies. `ab.limits` is ONE Facebook limit (`{ fb }`, 1 to 500) and `ab.typingSpeed` is `slow`/`normal`/`fast` (`TYPING_SPEEDS`; a Pro setting like the switches, the extension applies it to every job). The anti-ban page (`features/antiban`) opens with a card "the extension uses these settings" (what the browser applies when it posts, and that WHAT and WHERE it posts comes from the schedule: links to schedules, post library, group links and the team page); nothing there is "saved only" any more. The offline "notify" policy, the LINE/email/push channels and the offline banner's "queue"/"notify" buttons stay disabled with a "not supported yet" note (the offline notification events are never sent).
  - `ExtensionStore` runs the offline simulation through `/engine/extension` (`toggleSimulation()`, keyed on `simulatedOffline`, not on whether a device really is online) and `/engine/waiting/skip` (`skipWaiting()`); `unpaired` (only once `/engine` has answered)/`simulated` decide what the top bar and the offline banner show. Pausing the jobs of a browser is a device control (`DevicesStore.update`: the team page and the schedules' hand-over panel). There is no extension preview page any more (it was the popup mock with sample data); `/app/extension` redirects to the team page and `/app/campaigns` (the extension's old settings page, which installed extensions of older versions still open after pairing) to the anti-ban page.
  - `DevicesStore` lists the browsers paired to the workspace, creates pairing codes, renames them (`rename`: names are unique in a workspace, case-insensitive; the server refuses a taken name with a 422 and a Thai reason that the rename dialog shows inline, the request is quiet and the list keeps the old name; `nameTaken`/`freeName` mirror the server's "name (2)" numbering for hints), pauses their jobs (`update`, `PUT /devices/{id}`) and unbinds them. The extension has no settings of its own any more (2.2+: status page only), so pairing starts here: `features/team/PairDeviceModalComponent` creates a code and "Connect this Chrome" opens `connectUrl()` = `<origin>/connect-extension#ap-pair=1&code=…&name=…&ws=…` in a new tab; the extension of that Chrome takes the tab over, asks for one "Allow" and pairs with this origin's `/api`. "Copy connect link" gives the same address for ANOTHER computer or Chrome profile, which need not be signed in to the web app at all (or may be signed in as someone else): the extension only says "connected successfully" there, so the web never assumes the pairing browser is its own. The name field says names are unique and shows the name the extension will get ("Chrome 6/10/2569 (2)" when taken); the dialog polls the device list every 3 s, closes when a new device appears (wherever it paired from) and its toast names the final name. The top bar shows "n/m extensions online" when there are several (`SettingsStore.devicesOnline/devices`). The list follows the event stream (`device.online`/`paired`/`revoked`/`updated`, a re-read on every reconnect, a 60 s poll only while the stream is down), so the online dots stay current. `features/public/ConnectExtensionPageComponent` (route `/connect-extension`, no guard) only shows when no extension took the tab over. The team page has the rename / pause / unbind controls (owner and admin).
  - `LibraryStore` lists and uploads media and creates snippets (media carries a use count that the API records; snippets have none, so their cards show none). Files can be renamed (`renameMedia`), switched on/off (`setMediaActive`, in bulk) and deleted (`deleteMedia`, at most 500 per request; it also takes the ids off the new post's draft and re-reads the collections and the post library through `PostsSync`, because the server strips them from posts); snippets can be edited, switched on/off and deleted. An off file or snippet stays in the library but its "use" button is disabled. `upload(files, folderId?, refusals?)` returns the accepted ids and, when the caller passes `refusals`, collects the server's reason for each refused file (the plan's image limit). Image thumbnails are fetched as blobs with the token and shown through object URLs (an `<img src>` cannot send the header).
  - `DraftStore` holds the draft of a NEW post only (`text`, `media`, `collectionIds`): what the post editor holds while a post is being written. It survives a trip to the media library (the library page shows a "draft bar" that leads back to `/app/posts?new=1`; its "use" buttons fill the draft) and is dropped when the workspace changes; an existing post is edited with the editor's own state, never through the draft. `open(collectionId)` is what `?new=1&collection=` does: it keeps the text and makes that collection THE collection of the draft. Inputs stop at what the API accepts (`core/http/input-limits.ts`: post text 5000, media 20, collection name/description, hashtags, page tags, footer, the AI writer's fields (topic 300, a point 200, 10 points), snippet title 120 and text 2000, workspace name 120, device name 80).
  - **The post editor** (`features/posts/post-editor`, strings `t().api.flow.ed*`): ONE editor for a new post and an existing one, shown as a full-width panel at the top of `/app/posts` (form on the left, a sticky live preview on the right, one column on a phone). `PostsPageComponent` takes the route inputs `new` (alias of `openNew`), `collection` and `post`: `?new=1&collection=<id>` opens it empty (in that collection), `?post=<id>` opens a post once the library has arrived, and the panel writes its state back into the address; a card's "edit" and the "new post" button open it, the old `/app/composer?collection=&post=` address redirects (`composerRedirect` in `features/posts/posts-link.ts`, which also builds every link to it: `newPostParams`, `editPostParams`). The toolbar right above the text (always visible) writes at the caret (selectionStart/End, `insertAt`/`insertCodeTag`/`wrapSpin` in `core/flow/compose.ts`): `{{code}}`, a Spintax popover (ready-made sets, a custom `{a|b|c}` form, wrap the selection as `{selection|}`), saved snippets (only the ones switched on), the AI button and the "?" help. Under the text a status line says whether it has `{{code}}` (or that the code goes on line 1), `spinCount` ("N groups ≈ M variants") and `lintSpin` warnings (unbalanced braces, `{a}` with no pipe, empty options, `{{code}}` inside a group). The preview (`post-preview`) composes with `composeSegments` (highlights what spintax picked), has "reshuffle", "show 3 variants" (`spinVariants`), a link set and a group select (the group's code), a "preview as" collection for a post in several, the post's own live hashtags / footer / position over the collection's (`postComposeSettings`), and counts the composed length against `MAX_COMPOSED_LENGTH` (7,000). `app-pop` is the small popover the toolbar uses. A post in no collection is edited here like any other.
  - **AI post writer** (`core/data/ai.store.ts`, `features/posts/ai-panel`): `AiStore` reads `GET ai/status` (`enabled` = the server has an AI key, `allowed` = the owner's plan includes it, `draftsLeftToday`, null = no limit) when an editor first opens and again when the workspace changes, and `write()` calls `POST ai/posts` (drafts are never saved by the server). `state`/`canOpen`/`canWrite`/`reason` decide the buttons: nothing is enabled before the status has arrived (the AI button is a placeholder), and the AI button and the panel's Write button are disabled, with a visible reason and a `title`, while there is no key ("the admin has to set up an AI key"), the plan has no AI, or the person cannot edit. The panel (topic, selling points with Enter, four tones, 1-3 drafts) shows the drafts as cards: "Use this" replaces the editor's text, "Append" adds after it, "Add as a separate post" saves the draft as another library post SWITCHED OFF (the editor does the saving; the panel never saves). Errors are shown inline (the requests are `QUIET`).
  - **The post library** (step 1 of the flow, `/app/posts`, `features/posts`, strings in the `flow` pack as `t().api.flow.pl*`): a post is a shared master record that manages itself and that collections only include (one post may sit in many, `collectionIds`; CollectionPostDto has no `collectionId` any more). `MasterPostsStore` (`GET master-posts`, oldest first; `create`/`update`/`bulk` wait for the server and reject, `setActive`/`remove`/`approval` are optimistic with rollback and answer a boolean, `activity(id)` is the per-group results; `counts` feeds the filters) and `CollectionsStore` keep each other current through `PostsSync` (`core/data/posts-sync.ts`): each registers its quiet `refresh()` there and a mutation asks the other one to read again; a store that was never used is not created by this (so a page that needs one of them loads only that one). `CollectionsStore` post methods: `addPost`/`addPosts` write NEW posts into a collection, `addExistingPosts` puts library posts in (`POST collections/{id}/posts/add`), `updatePost(collectionId, post, change)` edits (text/media shown in every copy; `toCollectionId` moves), `removePost(collectionId, postId)` takes the post out of THAT collection only (the post stays in the library; deleting for good is `MasterPostsStore.remove`), `setApproval(collectionId, post, action)` (approval belongs to the post and shows in every copy); deleting a collection leaves its posts in the library. The page: search, state filters (all / on / off / awaiting approval / in no collection, with counts), a collection filter, 20 per page, per-post cards (`master-post-card`: switch, collection chips, posted / queued / failed / last / next, approval buttons, results from the activity endpoint, an "edit" button that opens the editor panel, delete confirmation owned by the page), a bulk bar (activate, deactivate, add to / remove from a collection, delete with confirmation) and the editor (`post-editor`: text, media picked from the library, collections (50 at most), own hashtags / footer / footer position each either following the collection or its own, own schedule limits: dates, weekdays, time window, a daily cap). The collections page adds "add from the library" (`AddFromLibraryModalComponent`, which reads the library only while open), an "in N collections" chip and an "off" badge on a row, and its row button means "take out of this collection".
  - The posting flow's stores (all root signal stores that reset with the workspace, load through `loadWithRetry`, and expose `loaded`): `CollectionsStore` (collections with their posts; edits to a collection apply at once and save one COMPLETE `PUT` 800 ms later, a refusal returns to the last confirmed values; post add/update wait for the server, taking a post out and approval are optimistic; first collection starts open), `LinkSetsStore` (sets and links; inline link edits are optimistic with a 600 ms per-row debounce and a complete `PUT` body; refreshes on `links.changed`/`post` events, on stream resume and by a 60 s poll while the stream is down; `exampleSettings` is the first collection's composing settings), `SchedulesStore` (schedules; `create`/`setActive`/`rename`/`remove` are pessimistic and then re-read posts, collections and link sets so the `scheduleCount`s stay right; `usingCollection`/`usingLinkSet` name the schedules for hints and refusals; `bestTimes()`). Every list item can be renamed, switched on/off and deleted from its own card: collections (`CollectionsStore.rename`/`setActive`/`remove`; a collection a schedule uses cannot be deleted), link sets (`LinkSetsStore.updateSet({name})`/`setActive`/`deleteSet`), schedules (`SchedulesStore.rename`/`setActive`/`remove`), library files and snippets. An off collection or link set is dimmed with a hint, makes its schedules queue nothing (the server drops their future queued posts and refills them when it is switched on again; the caller re-reads the schedules) and is marked "inactive" in the schedule builder, which refuses it. The shared dialogs are `app-rename-modal` (a `save` function; stays open with a message while it rejects) and `app-confirm-modal` (an `action` function); the on/off switch is `app-checkbox`, icon buttons use `.ibtn`/`.rowtools`. The four pages (posts, collections, link sets, schedules) share the stepper `app-flow-steps` (1 posts, 2 collections, 3 link sets, 4 schedules; the post editor, a panel of the post library, belongs to step 1) and the simple-mode `app-next-step`; `UiPrefsService.simple` (default on, localStorage `ap-simple`) decides which sidebar items show and whether the "more options" sections start collapsed (collections page tools, schedule builder, link-set options; each remembers the person's own choice). Query params open the schedule builder prefilled (`?collection=`, `?set=`, `?start=<yyyy-MM-dd>`, `?new=1`); the builder's "start posting" choice (the "more options" section also has the repeat choice, `ScheduleFormService.repeat` = `recent`/`any`/`never`, off with a note for the rotate order: may a group get a post it already had; `ScheduleFormService.startMode`: `time` = the schedule's times and start date, `now` = `startNow: true`, an opening round the moment it is created, the date field hidden and a Once schedule's time ignored) is not part of the prefill; a `start` that has already passed becomes today, and the calendar's "add" is off on a past day. The builder warns (`ScheduleFormService.overLimit`, `.over` above its foot) when the Facebook posts of a day (the groups plus the set's Facebook accounts, own times counted) go over the workspace's Facebook daily limit, with a link to the anti-ban page (which accepts up to `INPUT_LIMITS.platformDailyLimit`, 500): the server would fail the rest as `quota`. A schedule bigger than 2,000 posts is fine: the server makes it in whole days, 2,000 at most per run, and the next claim makes the rest. `features/schedules/ScheduleDispatchComponent` ("hand-over to the extension", between the builder and the schedule list; hidden while no browser is paired) shows each paired browser as ready / offline / paused from the web (with "resume") / paused by the engine (`autoPauseLine`), today's queue (the post going out, else how many wait and the next time) and "take jobs now" (`DevicesStore.takeJobs`, the `takeJobs` device command; editors, ready browsers only), and says that the browser posts exactly what the schedule says and that its behaviour (typing, scrolling, the rest after a block) is set on the anti-ban page (link). The suggested posting hours (`SchedulesStore.best`/`askBest()`, a quiet request) belong to the workspace and empty with it. Things the server only stores (watermark, image shuffle, auto-delete, remote bot commands, auto-reply rules) carry the `storedOnly` hint. BUMP is real (a Premium feature): the schedule builder's `schedule-bump` section (`ScheduleFormService.bumpOn/bumpHours/bumpRounds/bumpText/bumpMedia/bumpEach`, library images picked as thumbnails, locked with `app-feature-lock` while `WorkspaceStore.bumpLocked`) sends `bumpHours` + `bump {rounds, text, mediaIds, imagesEach}`, never `bumpHours > 0` when locked (the API answers 403); page tags travel with every job.
  - `NotificationsStore` (settings copy with `dirty`/`locked`; bot and channel tokens are write-only: kept apart in `tokens`, null keeps, '' removes, text replaces, never put back into the loaded settings; `save()` sends the whole body, `testChannel` saves first when dirty, `findChats`; rules back at their defaults are dropped from the body), `AutoReplyStore` (rules saved as a whole list, optimistic with rollback; `matchRule` is the client-side "try it" matcher; nothing executes the rules and there is no comment feed), `ReportsStore` (7 or 30 days; `disableGroup` switches off every link with that address; `share()` makes the client report link, `shares` lists the links still live (`ensureShares`/`loadShares`, admins of an Agency workspace only, read again after each `share()`) and `revokeShare(id)` switches one off; likes and comments do not exist, the columns show "—"), `TestPostStore` (one real post, due now, through ONE extension: `deviceId` is the one picked, else the one the link set posts as (`postAsAccountId`'s device, link set panel only), else the first online one, and the page shows a picker above both panels (plain text when there is one extension; no extension / none online / the chosen one offline disable the buttons with a banner). Two panels share the extension, the log and the history, `panel` says which one shows: "from a collection" (`run()` = `POST test-post` with the set, group or page, collection, post and optional text) and "by hand" (`runManual()` = `POST test-post/manual`: a group or page link read with `facebookTarget`, a text of at most 5,000 characters whose spintax the server resolves, at most `TEST_MAX_MEDIA` (10) library images, picked from `LibraryStore` or uploaded through it, so they count toward the plan's image limit and the server's refusal is shown). Both then follow the post by id from `post` events and a 3 s poll until success / failed / pending / skipped, a "still waiting" line after 3 minutes; the log is real, nothing is simulated; `features/test` is a page plus two forms) and `BackupStore` (download / restore of the whole workspace as JSON; the restore dialog works in two steps: "Check the file" refuses a text that is not a complete backup and lists what the file holds (`summarizeBackup` in `core/flow/backup-summary.ts`: posts counted once per `key`, plus the posts that sit in no collection) and what is replaced, and only a second click ("Replace and restore") sends it, admins only; a restore re-reads collections, link sets, schedules, posts, engine settings, notifications and auto-reply). Notifications, auto-reply, advanced anti-ban and backup are gated by the OWNER's plan flags on the workspace (`notifications`, `autoReply`, `advancedAntiBan`, `clientReports`); locked pages keep their content visible but disabled with `app-feature-lock` (Upgrade shown to the owner only). A lock is only decided once `WorkspaceStore.loaded()` is true (`NotificationsStore.locked`, `AutoReplyStore.locked`, `ReportsStore.shareLocked`, the anti-ban page's `locked`): before that nothing shows as locked, so a reload does not flash the banner.
  - Pure helpers in `core/flow/` (no Angular, mirrored from the server's rules and unit-tested): `group-links` (URL normalisation to `https://www.facebook.com/groups/<slug>`, bulk `url | code` parsing, CSV import/export), `compose` (spintax resolved in rounds like the server: every innermost group at once, at most 50 rounds, `{{code}}`, footer, hashtags, `postComposeSettings` for a post's own overrides; plus the editor's helpers `insertAt`, `insertCodeTag`, `wrapSpin`, `buildSpin`, `lintSpin`, `spinCount`, `composeSegments`, `spinVariants`), `schedule-math` (slots, which days match — weekend is Fri–Sun —, time parsing, drip/interval/once, best hours, the browser's UTC offset), and `download`. Keep them in step with `PostComposer`, `FacebookGroupUrl` and `Schedule` in the backend.
  - `TeamStore` lists the current workspace's people (`/members`: the owner row has `id` null, pending invitations have `active` false), invites, changes roles and removes or leaves. `role`/`canManage` come from `PermissionsService`; `seatLimit`/`seatsFull` from the workspace's limits (owner and pending invitations take a seat). The team page turns inviting off when the plan has one seat or the seats are taken, and "add device" off when the plan's devices are paired; the server enforces seats, devices and roles (403 for too low a role). A role `<select>` goes back to the member's role when the update fails.
  - `AdminStore` holds the platform-admin data from `/api/admin/*` (customers, transactions, promo codes, subscription counts, 12 months of revenue, jobs) and the plans from the public `/api/plans`. `loadPlans()` runs in the app initializer; `load()` runs each time an admin page is entered (the `loadAdminData` `canActivateChild` guard in `admin.routes.ts`; it does not wait, the pages show "—" until `loaded`) and never throws. Every action re-reads what it may have moved (money, health figures, the customer's activity log). The data belongs to the signed-in user: another sign-in, or an assist session, empties it and drops late answers. Money dates (transactions, promo expiry, the finance page's "this month") use the Bangkok calendar like the server (`bangkokParts`); "today" elsewhere stays local. Plan limits in `AdminStore.plans` feed the plan cards (`limitLines()`/`featureLines()`/`compareRows()` in `plans.ts`: the seven numbers (accounts, posts per 24 h, devices, seats, Facebook groups and pages, image library, post library) and the six functions (AI drafts, advanced anti-ban, notifications, auto-reply, bump, client reports) of each plan, from `/api/plans`; `core/data/usage.ts` `usageOf(used, limit)` makes the "n / limit" rows of the billing page; the key `agency` is shown as "Premium") and the admin pages (the plan editor takes the seven numbers and lists the functions read-only, the customer page overrides the seven). `WorkspaceStore` carries the owner's plan flags (`advancedAntiBan`, `notifications`, `autoReply`, `clientReports`, `ai`, `bump`; `aiLocked`/`bumpLocked` only decide once `loaded()`). The server refuses (422, Thai reason) when adding a group, an image or a library post would go over the package.

  - Billing (Stripe; nothing about a card is stored or typed here). `BillingStore` (`core/data/billing.store.ts`) holds `GET /api/billing` (`info`: plan, cycle, status, `hasSubscription`, `renewsAt`, `cancelAtPeriodEnd`, the card Stripe has on file, `paymentsEnabled`, the signed-in customer's own `limits` and real `usage`) and `GET /api/billing/invoices` (charges, refunds and failed payments with Stripe's `receiptUrl`); `openPortal()` (`POST /api/billing/portal`) and `checkout(url)` leave the app through `RedirectService` (a service so specs can replace `window.location.assign`). `SessionStore.setPlan(plan, cycle, promoCode)` is `PUT /api/billing/plan`: it answers a Checkout address for a first paid plan (the page redirects to Stripe) or `null` when the plan changed on the server (a customer with a subscription: Stripe bills the difference at once, a declined card leaves the plan as it was; choosing Free schedules the cancellation for the end of the period; choosing the current plan again takes it back). **The plan in the UI only changes when the server says so**: the billing page (`/app/billing`) handles the return from Checkout (`?checkout=success&session_id=…` → `confirmCheckout`, `?checkout=cancel`) and the plan picked on the landing page (`?plan=`, passed through sign-up by `AuthPageComponent.welcome()`), and the webhook may apply the plan before or after that. Without a Stripe key the API answers `paymentsEnabled: false` and the page says online payment is off. A promo code is asked for only when a new subscription starts (it discounts the first invoice). The card and invoices are managed in Stripe's portal ("manage payment"). Admin: refunds and "retry payment" call Stripe through the API (`adminRefund`, `adminRefundLatest`, `adminRetryPayment`) and the finance page shows the amounts the API returns. Nothing here has been run against live Stripe.
  - **In-app payment window** (`features/billing/payment-checkout`, `shared/components/payment-method-list`, `core/data/payment.store.ts`, `core/payments`; the backend's `docs/payment-checkout.md` explains the whole design). When `GET /api/billing/payment-config` has a `publishableKey` (`PaymentStore.ready()`), choosing a first paid plan on the billing page opens `app-payment-checkout` instead of redirecting to Stripe Checkout (no key = the old redirect; `SessionStore.setPlan` is not called, so nothing changes until Stripe confirms). The window lists the five ways to pay with `app-payment-method-list` (a radio group, own inline icons, the picked row opens its form from the projected `<ng-template>`, arrow/Home/End keys) in the fixed order card, Apple Pay, Google Pay, Link, PromptPay (`PAYMENT_METHODS`); a wallet the device cannot use is explained, not hidden. Behind the rows is Stripe.js, loaded from js.stripe.com by `StripeService` (`@stripe/stripe-js`; never bundled, card data only goes into Stripe's iframes): card = card element + `confirmCardPayment`; Apple Pay / Google Pay / Link = an Express Checkout Element showing only that wallet (`ready` says whether the device can use it, `loaderror` too) + `confirmPayment`; PromptPay = `confirmPromptPayPayment` (Stripe's QR modal). One PaymentIntent per flow (`flowOf`: card and wallets share a subscription payment, PromptPay is a separate one-period prepaid payment) is made by `POST /api/billing/payments` when its first row opens. Whatever Stripe.js says, the window then asks `POST /api/billing/payments/{id}/confirm` (`PaymentStore.settle`: every 2 s while `pending`, up to 15 min, stops on abort) and only the server's `succeeded` shows "paid" and updates the session (`SessionStore.applyUser`); a throwing Stripe.js call is reported to `ErrorHandler` and the window goes back to ready (never stuck on "paying"). A PromptPay plan has an end date and no subscription (`renewsAt` set, `hasSubscription` false): the billing page says "prepaid, valid until" and lets the current plan be paid for again (adds a period); choosing Free only lets it run out. A payment that left the page comes back as `?payment_intent=pi_...` and is applied the same way. Specs fake Stripe.js (`payment-checkout.component.spec.ts`) and replace `StripeService` in `billing-page.component.spec.ts`, so no spec touches the network. Not yet exercised against a real Stripe account.

  - The admin's real payment test (`/app/admin/payment-test`, `features/admin/payment-test-page`, strings `t().api.ptest*`; talks to `ApiService.adminPaymentOverride()`/`adminSetPaymentOverride()` directly, no store): a switch, a baht amount (whole number from the API's `minAmount`, 10, to 1,000,000) and the e-mails of the customers who pay that amount at Stripe instead of the plan's price (one per line or comma separated, ≤20; the page and the API refuse turning it on for nobody). It shows what the API holds (`state`, last change) apart from the unsaved form, warns that real money moves and that renewals keep charging the amount, and lists the `payment_override_changed`/`payment_override_used` entries of the platform-wide log (`AdminStore.globalAudit`; `AdminViewService.auditRow` turns the API's `on amount=20 emails=1` into text).
  - `AdminStore.health` (`/api/admin/health`) feeds the admin overview's KPIs and system-health panel; `AdminStore.audit` (`/api/admin/audit?customerId=`) is the customer page's activity log and `globalAudit` (no customer) the plan and promo-code changes on the plans page; both are re-read after every action. Promo codes show as active, switched off or expired (past `expiresAt`), can be switched, and a new code is 3-30 letters or digits like the API's. The customer page compares what the API counts the way it counts it: accounts and posts (published in 24 h, never the failed ones) are owner-wide, devices and seats are per workspace.
  - Assist mode: "assist" on a customer calls `SessionStore.startAssist(id)`, which keeps the admin's token in `ap-assist` (`assistStorage`) and signs in with the customer's one-hour, read-only token. `AppLayoutComponent` shows the assist banner with "back to admin" (`endAssist()`); an expired assist token (401 in `authInterceptor`, or at `restore()`) also goes back to the admin. `WorkspaceStore` reloads whenever the signed-in user's id changes, so the switch reloads every workspace store.
  - `DeviceEventsService` (`core/data/device-events.service.ts`) is the workspace's live event stream: `GET /api/workspaces/{ws}/events/stream` (Server-Sent Events) read with `fetch` + `ReadableStream` so the bearer token travels in a header. One connection per workspace while anyone is subscribed (`subscribe(handler)`), reconnect with backoff and jitter, a 45 s stall detector (the server pings every 15 s), and `?after=<lastSeq>` on reconnect so the server first replays what was missed (the API sends `event: reconnect` when it rotates, shuts down or the backlog is too big). `connected`/`lastSeq`/`reconnects` are signals; `onResume(fn)` runs after every (re)connect so a store refetches what it shows. Stores keep a slow poll as the fallback. A 401, 403 or 404 on the stream stops it for good; the service ends its connection and listeners when its injector is destroyed. Event types and payloads: `DeviceEventType` in the backend. Import/export use the extension's `backup.js`, `zip.js` and `siri-import.js`.
  - **Sample data is only the landing page's:** `core/data/sample.ts` (the design's post generator and texts, Facebook only: `tools/facebook-only.mjs` keeps `import:design` that way) feeds the landing-page preview, so `seed.data.ts` ships in the landing page's chunk; the Facebook name/icon (`core/data/platforms.ts`), month and weekday names (`core/i18n/calendar.ts`) and the design's plan defaults (`DESIGN_PLANS`, shown until `/api/plans` answers) are small constants outside it. Nothing in the workspace screens is sample data.
- **Errors.** `core/http/problem-details.ts`: `problemOf(e)?.title` is the API's Thai message, `problemMessage(e)` the first field message else the title, `fieldErrors(e)` the messages by field; forms that send `QUIET` requests (invite, pairing, login) show them inline. A 403 on login means a suspended or banned account (`t().api.blocked`). `ago(t, date)` in `i18n.service.ts` formats last-seen times.
- **Derived views.** `DashboardStatsService` builds the KPIs, today's queue, the trend, the paired extensions (`extensionRows`, from `DevicesStore`) and recent errors for the overview; its pure helpers `kpisOf`/`queueRowsOf` also build the landing preview from sample posts. `core/data/plans.ts` builds the plan cards. `features/admin/AdminViewService` is provided in `admin.routes.ts` and holds the MRR, transaction rows, effective limits and job rows.
- **i18n.** `core/i18n/i18n.data.ts` is generated. Every leaf is a `[th, en]` pair, and `I18nService.t()` is a computed, typed dictionary for the current language. `core/i18n/i18n.fixes.ts` is a typed override layer (`Fixes<typeof AP_I18N>`: only existing leaves, both languages) deep-merged over the generated dictionary by `applyFixes()`; every corrected leaf carries a comment saying what the design got wrong (no 14-day trial, failure reasons that are TikTok/LINE samples, "rolls over to tomorrow", "same day" windows, reminders that nothing sends, a fixed version number, a prototype "AI" note that is not true any more now that the writer is a real model). Fix copy there, not in `i18n.data.ts`, so a re-import cannot undo it. The first bundle stays under its budget, so big blocks of strings live in lazy packs that follow one pattern through `registerPack(name, part)`: `i18n.flow.ts` (`t().api.flow`: post editor, collections, link sets, schedules, calendar, overview) and `i18n.engine.ts` (`t().api.engine`: test post, notifications, auto-reply, reports, anti-ban, backup, devices); import the pack in every file that reads it and append leaves under a comment block of your feature. Do not confuse `t().flow.*` (the design's stepper texts) with `t().api.flow.*` (the pack). Templates read `t().section.key` and fill `{placeholders}` with `fmt()`. - **Known limits (deliberate, not bugs to chase).**

## Legacy app (`legacy/`)

```bash
cd legacy && npm install && npm run dev   # http://localhost:5173, proxies /api to VITE_BACKEND_URL (default http://localhost:8080)
```

If the legacy backend runs with `dotnet run`, it listens on 5080, so set `VITE_BACKEND_URL` to match. Every API call uses the cookie `fbap.auth` with `credentials: 'same-origin'`, so the page and the API must share an origin. `legacy/nginx.conf` proxies `/api/` to `http://backend:8080`.

- Pages: `index.html` + `web/admin.js` manage profiles and devices. `login.html` is the cookie login. `dashboard.html` + `dashboard.js` + `lib/*` are the extension's own settings page, reused as-is.
- `web/shim.js` loads before `dashboard.js` and fakes the `chrome` API on top of the legacy REST API:
  - The `settings` key maps to `/api/profiles/{id}/settings` with `baseRevision`; a 409 means the page must reload.
  - `img:<id>` keys map to `/api/profiles/{id}/images/*`.
  - `state` and `logs` come from polling `/api/devices/{id}/live`.
  - `sendMessage` becomes `POST /api/devices/{id}/commands` followed by polling `/api/commands/{id}`. Commands in `LOCAL_ONLY` are refused.
