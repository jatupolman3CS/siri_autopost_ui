# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

The frontend for AutoPost, a SaaS that posts to Facebook groups and other social accounts through a browser extension. The repo holds two apps:

- **Root:** an Angular 22 app (standalone, zoneless, signals, SCSS, Vitest) that implements the "AutoPost Dashboard" design from a Claude Design handoff. It covers the landing page, login/signup, the workspace screens (overview, the collection → link set → schedule flow, calendar, library, reports, test post, anti-ban, notifications, auto-reply, offline, errors, billing, team, extension preview), the public client report (`/report/:token`) and 6 platform-admin screens.
- **`legacy/`:** the old Vite-hosted copy of the extension's dashboard, which talks to the legacy server `backend/SIRI.AUTOPOST.Server` in `siri_autopost_backend`. See "Legacy app" below.

User-facing text comes from the TH/EN dictionary, never from literals in templates (toast and error fallbacks in `core/http` are the only exception). Strings the design handoff lacks go in `core/i18n/i18n.extra.ts` (`t().api.*`; the campaigns screen's own strings are in `core/i18n/i18n.ext.ts`, `t().api.ext.*`), not in the generated `i18n.data.ts`. Copy of the design that contradicts what the system does is corrected in `core/i18n/i18n.fixes.ts`, never in the generated file (see "i18n"). Messages computed by the extension's own libraries (`campaignProblem`, import errors) stay Thai. Code comments are in English.

`src/app/core/ext/lib/{shared,backup,zip,siri-import}.js` are byte-identical copies of `client/lib/*` in `siri_autopost_backend` (typed by the `.d.ts` files next to them, which must follow any change of the exported API). Prettier does not touch them; copy them again when the extension's libraries change.

## Commands (Angular app)

```bash
npm install
npm start                 # ng serve on :4200 (proxy.conf.json sends /api to SIRIAUTOPOST.Api on http://localhost:5100; start it first)
npx ng test --watch=false # unit tests, single run (npm test = watch mode)
npx ng test --watch=false --include src/app/core/data/posts.store.spec.ts   # one spec
npm run build             # production build -> dist/siri-autopost-ui/browser
npm run format            # prettier (the only formatter; no ESLint)
npx prettier --check .    # the whole repo; .prettierignore skips legacy/, the extension libs, the API snapshot and prose
npm run import:design -- <autopost-data.js>   # regenerate i18n.data.ts + seed.data.ts from a design handoff
npm run gen:api           # openapi.snapshot.json -> src/app/core/http/api-schema.ts (prettier-formatted)
docker build -t siriautopost-web .   # nginx image: dist + /api proxy to http://api:8080 (nginx.conf)
```

The whole stack (PostgreSQL + API + this app) runs with `docker-compose.saas.yml` in `siri_autopost_backend`, which builds this repo from `UI_PATH` (default `../siri_autopost_ui`).

Angular CLI 22 needs Node ≥ 22.22.3 (or ≥ 24.15).

CI (`.github/workflows/ci.yml`) runs `prettier --check`, checks that `npm run gen:api` leaves `api-schema.ts` unchanged (commit the regenerated file with the snapshot), builds, runs the unit tests, builds `legacy/` and the Docker image.

## Architecture (Angular app)

- **Data comes from `SIRIAUTOPOST.Api`** (backend repo). `core/http/api.service.ts` is the only place that calls `HttpClient`: typed methods (types from `api-schema.ts`) that return promises. `core/data/*.store.ts` are `providedIn: 'root'` signal stores on top of it; pages read their signals and await their methods. Every store loader runs through `loadWithRetry` (`core/data/loading.ts`): a server that is down or busy (0, 408, 429, 5xx) is asked again after 2, 5 and 15 s, a refusal (4xx) is not, it never rejects, and an answer for a workspace or user that has gone meanwhile is dropped. The stores that load data have a `loaded` flag the pages read, so a page shows "—" rather than 0 or 100% before its data has arrived. Stores empty themselves when the workspace or the user changes (settings, draft, offline timestamp, admin data), so one workspace's values are never saved into another.
- **Auth.** `SessionStore` logs in/signs up against `/api/auth`, keeps the JWT in localStorage (`ap-token`, `core/auth/token.ts`) and checks it with `/api/auth/me` in `provideAppInitializer` before the first navigation. `restore()` drops the token only on a 401 (a server that cannot answer keeps it and sets `restoreFailed`, which the login page says). `authInterceptor` adds the bearer header and sends the user to `/login` on a 401; `signedInGuard` and the interceptor pass the wanted address as `?returnUrl=` and `AuthPageComponent` goes back there after signing in (`safeReturnUrl`: pages of the app only). `errorInterceptor` toasts failures except 401s and requests sent with the `QUIET` context (login, signup, uploads, background refreshes), whose callers show their own errors; a 400 toasts its first field message (else its title), and `NotificationService` does not stack an identical toast. The role (`user`/`admin`) and plan come from the server.
- **Workspaces.** `WorkspaceStore` loads the user's workspaces after sign-in and remembers the current one (`ap-ws`). Each workspace carries the *owner's* effective `limits` (plan plus the platform admin's overrides: accounts, posts per 24 h, devices, seats; null = unlimited) and `advancedAntiBan`, whatever plan the signed-in member has; the list is read again when the user's plan changes. Workspace-scoped stores call `whenWorkspaceChanges()` in their constructor to reset and reload when it changes (and to empty themselves on sign-out). Limits shown anywhere (team seats and devices, the popup, the anti-ban lock) come from there or from `GET /api/billing`, never from `plans()[session.plan()]`.
- **Permissions.** `PermissionsService` is the one place that decides what the signed-in person may do in the current workspace, from its role (viewer < editor < admin < owner) and assist mode (read-only for everything): `canEdit` (posts, library, reconnect, skip waiting, campaigns and extension commands), `canAdmin` (anti-ban and offline settings, the offline simulation, devices, members), `readOnly`, `canCreateWorkspace` and the hint texts (`editHint`/`adminHint`). Every control the API would answer with a 403 binds `[disabled]` to it, with a `title` hint, and `<app-perm-note level="edit|admin">` says why under the page title. A viewer must never be able to click something that is certain to fail.
- **Stores.**
  - `PostsStore` loads posts a calendar month at a time (`ensureMonth`, which rejects when the API does; the months around today on load, the calendar asks for the rest) plus the open error reports, and `refresh()` re-reads both after every change and never throws. `loaded` is set once the first months and the errors are in. `items`/`byDay`/`today` add a day key and HH:MM (the local day); `postRow()` builds a list row. `now` is a signal that ticks every 30 s.
  - `AccountsStore` holds the social accounts (health, groups, `connected`); `reconnect()` marks one signed in again. `accountKind()` (models.ts) tells a `connected` account (a browser posts for it), an `unbound` one (its browser was revoked: the API names it "Facebook · <browser>", it keeps its history and cannot post) and a `sample` one (the demo accounts of a new workspace: never sent, labelled "ตัวอย่าง"). The list follows the event stream (`device.groups`/`updated`/`paired`/`revoked` and `post` events, a re-read on every reconnect of the stream, a 60 s poll only while the stream is down).
  - `SettingsStore` holds the anti-ban and offline settings from `/engine` (edited locally, sent by `saveAb()`/`saveOff()`, which do nothing before `loaded`), the extension's presence (`extensionOnline`, `simulatedOffline`, `devices`, `devicesOnline`), and `used24h`: posts that went out in the last 24 hours per platform on connected accounts, success and awaiting approval, which is what the server counts against the daily limits (sample accounts and their history never count). Every minute it refreshes only the presence (quietly, so edits in progress survive) and, when a device is paired, the posts; in between, `device.online`/`device.paired`/`device.revoked` events refresh the presence and `post` events refresh the posts at once. Billing preferences stay local. `ab.advanced` carries the workspace-wide rules (min gap, overall daily cap, block pause hours, failure streak, recent avoid, cooldown, auto-off fails, stop at failure %, focus window; `patchAdvanced()`): the server enforces them and the auto-pause and warm-up switches (Pro and above; below it the stored values stay and the inputs are disabled), while the focus window is stored only and says so (`t().api.engine.storedOnly`); shuffle is the order of the groups inside a schedule slot, which the schedule engine applies. The offline "notify" policy, the LINE/email/push channels and the offline banner's "queue"/"notify" buttons stay disabled with a "not supported yet" note (the offline notification events are never sent).
  - `ExtensionStore` runs the offline simulation through `/engine/extension` (`toggleSimulation()`, keyed on `simulatedOffline`, not on whether a device really is online) and `/engine/waiting/skip` (`skipWaiting()`); `unpaired` (only once `/engine` has answered)/`simulated` decide what the top bar and the offline banner show. `jobsPaused`/`togglePause()` on the popup preview are the real `jobsPaused` of the paired browsers (admins).
  - `DevicesStore` lists the browsers paired to the workspace, creates pairing codes, renames them or pauses their jobs (`update`, `PUT /devices/{id}`) and unbinds them. The extension has no settings of its own any more (2.2+: status page only), so pairing starts here: `features/team/PairDeviceModalComponent` creates a code and "Connect this Chrome" opens `connectUrl()` = `<origin>/connect-extension#ap-pair=1&code=…&name=…&ws=…` in a new tab; the extension of that Chrome takes the tab over, asks for one "Allow" and pairs with this origin's `/api`. The dialog polls the device list every 3 s and closes when a new device appears. The list follows the event stream (`device.online`/`paired`/`revoked`/`updated`, a re-read on every reconnect, a 60 s poll only while the stream is down), so the online dots stay current. `features/public/ConnectExtensionPageComponent` (route `/connect-extension`, no guard) only shows when no extension took the tab over. The team page and the campaigns page have the rename / pause / unbind controls (owner and admin).
  - `LibraryStore` lists and uploads media and creates snippets (media carries a use count that the API records; snippets have none, so their cards show none). Files can be renamed (`renameMedia`), switched on/off (`setMediaActive`, in bulk) and deleted (`deleteMedia`, at most 500 per request; it also takes the ids off the composer's draft and re-reads the collections and the post library through `PostsSync`, because the server strips them from posts); snippets can be edited, switched on/off and deleted. An off file or snippet stays in the library but its "use" button is disabled. Image thumbnails are fetched as blobs with the token and shown through object URLs (an `<img src>` cannot send the header).
  - `DraftStore` holds the composer's draft of ONE collection post (`text`, `media`, `collectionId`, `postId` when editing, `errText`/`errCol`); it survives a trip to the library (the library page shows a "draft bar") and is dropped when the workspace changes. Inputs stop at what the API accepts (`core/http/input-limits.ts`: post text 5000, media 20, collection name/description, hashtags, page tags, footer, the AI writer's fields, snippet title 120 and text 2000, workspace name 120, device name 80). The composer (`/app/composer?collection=&post=`) no longer schedules anything: it saves into a collection; the preview composes the text for a link set with `core/flow/compose.ts` exactly like the server (`PostComposer`), laying the post's own hashtags / footer / footer position over the collection's (`postComposeSettings`; null follows the collection, `""` means none). A post that sits in several collections is opened in the one the address names (`CollectionsStore.postById(id, preferred)`); a post in no collection cannot be opened in the composer (the post library's editor handles it).
  - **The post library** (step 1 of the flow, `/app/posts`, `features/posts`, strings in the `flow` pack as `t().api.flow.pl*`): a post is a shared master record that manages itself and that collections only include (one post may sit in many, `collectionIds`; CollectionPostDto has no `collectionId` any more). `MasterPostsStore` (`GET master-posts`, oldest first; `create`/`update`/`bulk` wait for the server and reject, `setActive`/`remove`/`approval` are optimistic with rollback and answer a boolean, `activity(id)` is the per-group results; `counts` feeds the filters) and `CollectionsStore` keep each other current through `PostsSync` (`core/data/posts-sync.ts`): each registers its quiet `refresh()` there and a mutation asks the other one to read again; a store that was never used is not created by this (so a page that needs one of them loads only that one). `CollectionsStore` post methods: `addPost`/`addPosts` write NEW posts into a collection, `addExistingPosts` puts library posts in (`POST collections/{id}/posts/add`), `updatePost(collectionId, post, change)` edits (text/media shown in every copy; `toCollectionId` moves), `removePost(collectionId, postId)` takes the post out of THAT collection only (the post stays in the library; deleting for good is `MasterPostsStore.remove`), `setApproval(collectionId, post, action)` (approval belongs to the post and shows in every copy); deleting a collection leaves its posts in the library. The page: search, state filters (all / on / off / awaiting approval / in no collection, with counts), a collection filter, 20 per page, per-post cards (`master-post-card`: switch, collection chips, posted / queued / failed / last / next, approval buttons, results from the activity endpoint, inline editor, delete confirmation owned by the page), a bulk bar (activate, deactivate, add to / remove from a collection, delete with confirmation) and the editor (`post-editor`: text, media picked from the library, collections (50 at most), own hashtags / footer / footer position each either following the collection or its own, own schedule limits: dates, weekdays, time window, a daily cap). The collections page adds "add from the library" (`AddFromLibraryModalComponent`, which reads the library only while open), an "in N collections" chip and an "off" badge on a row, and its row button means "take out of this collection".
  - The posting flow's stores (all root signal stores that reset with the workspace, load through `loadWithRetry`, and expose `loaded`): `CollectionsStore` (collections with their posts; edits to a collection apply at once and save one COMPLETE `PUT` 800 ms later, a refusal returns to the last confirmed values; post add/update wait for the server, taking a post out and approval are optimistic; first collection starts open), `LinkSetsStore` (sets and links; inline link edits are optimistic with a 600 ms per-row debounce and a complete `PUT` body; refreshes on `links.changed`/`post` events, on stream resume and by a 60 s poll while the stream is down; `exampleSettings` is the first collection's composing settings), `SchedulesStore` (schedules; `create`/`setActive`/`rename`/`remove` are pessimistic and then re-read posts, collections and link sets so the `scheduleCount`s stay right; `usingCollection`/`usingLinkSet` name the schedules for hints and refusals; `bestTimes()`). Every list item can be renamed, switched on/off and deleted from its own card: collections (`CollectionsStore.rename`/`setActive`/`remove`; a collection a schedule uses cannot be deleted), link sets (`LinkSetsStore.updateSet({name})`/`setActive`/`deleteSet`), schedules (`SchedulesStore.rename`/`setActive`/`remove`), library files and snippets. An off collection or link set is dimmed with a hint, makes its schedules queue nothing (the server drops their future queued posts and refills them when it is switched on again; the caller re-reads the schedules) and is marked "inactive" in the schedule builder, which refuses it. The shared dialogs are `app-rename-modal` (a `save` function; stays open with a message while it rejects) and `app-confirm-modal` (an `action` function); the on/off switch is `app-checkbox`, icon buttons use `.ibtn`/`.rowtools`. The four pages (posts, collections, link sets, schedules) share the stepper `app-flow-steps` (1 posts, 2 collections, 3 link sets, 4 schedules; the composer shows step 1) and the simple-mode `app-next-step`; `UiPrefsService.simple` (default on, localStorage `ap-simple`) decides which sidebar items show and whether the "more options" sections start collapsed (collections page tools, schedule builder, link-set options; each remembers the person's own choice). Query params open the schedule builder prefilled (`?collection=`, `?set=`, `?start=<yyyy-MM-dd>`, `?new=1`); the builder's "start posting" choice (the "more options" section also has the repeat choice, `ScheduleFormService.repeat` = `recent`/`any`/`never`, off with a note for the rotate order: may a group get a post it already had; `ScheduleFormService.startMode`: `time` = the schedule's times and start date, `now` = `startNow: true`, an opening round the moment it is created, the date field hidden and a Once schedule's time ignored) is not part of the prefill; a `start` that has already passed becomes today, and the calendar's "add" is off on a past day. `features/schedules/ScheduleDispatchComponent` ("hand-over to the extension", between the builder and the schedule list; hidden while no browser is paired) shows each paired browser as ready / offline / paused from the web (with "resume") / paused by the engine (`autoPauseLine`), today's queue (the post going out, else how many wait and the next time) and "take jobs now" (`DevicesStore.takeJobs`, the `takeJobs` device command; editors, ready browsers only), and links to the settings page. The suggested posting hours (`SchedulesStore.best`/`askBest()`, a quiet request) belong to the workspace and empty with it. Things the server only stores (page tags, watermark, image shuffle, bump, auto-delete, focus window, remote bot commands, auto-reply rules) carry the `storedOnly` hint.
  - `NotificationsStore` (settings copy with `dirty`/`locked`; bot and channel tokens are write-only: kept apart in `tokens`, null keeps, '' removes, text replaces, never put back into the loaded settings; `save()` sends the whole body, `testChannel` saves first when dirty, `findChats`; rules back at their defaults are dropped from the body), `AutoReplyStore` (rules saved as a whole list, optimistic with rollback; `matchRule` is the client-side "try it" matcher; nothing executes the rules and there is no comment feed), `ReportsStore` (7 or 30 days; `disableGroup` switches off every link with that address; `share()` makes the client report link, `shares` lists the links still live (`ensureShares`/`loadShares`, admins of an Agency workspace only, read again after each `share()`) and `revokeShare(id)` switches one off; likes and comments do not exist, the columns show "—"), `TestPostStore` (one real post through `POST test-post`, then followed by id from `post` events and a 3 s poll until success / failed / pending / skipped, a "still waiting" line after 3 minutes; the log is real, nothing is simulated) and `BackupStore` (download / restore of the whole workspace as JSON; the restore dialog works in two steps: "Check the file" refuses a text that is not a complete backup and lists what the file holds (`summarizeBackup` in `core/flow/backup-summary.ts`: posts counted once per `key`, plus the posts that sit in no collection) and what is replaced, and only a second click ("Replace and restore") sends it, admins only; a restore re-reads collections, link sets, schedules, posts, engine settings, notifications and auto-reply). Notifications, auto-reply, advanced anti-ban and backup are gated by the OWNER's plan flags on the workspace (`notifications`, `autoReply`, `advancedAntiBan`, `clientReports`); locked pages keep their content visible but disabled with `app-feature-lock` (Upgrade shown to the owner only). A lock is only decided once `WorkspaceStore.loaded()` is true (`NotificationsStore.locked`, `AutoReplyStore.locked`, `ReportsStore.shareLocked`, the anti-ban page's `locked`): before that nothing shows as locked, so a reload does not flash the banner.
  - Pure helpers in `core/flow/` (no Angular, mirrored from the server's rules and unit-tested): `group-links` (URL normalisation to `https://www.facebook.com/groups/<slug>`, bulk `url | code` parsing, CSV import/export), `compose` (spintax, `{{code}}`, footer, hashtags, `postComposeSettings` for a post's own overrides), `schedule-math` (slots, which days match — weekend is Fri–Sun —, time parsing, drip/interval/once, best hours, the browser's UTC offset), `ai-writer` (template-based post generator; there is no language model) and `download`. Keep them in step with `PostComposer`, `FacebookGroupUrl` and `Schedule` in the backend.
  - `TeamStore` lists the current workspace's people (`/members`: the owner row has `id` null, pending invitations have `active` false), invites, changes roles and removes or leaves. `role`/`canManage` come from `PermissionsService`; `seatLimit`/`seatsFull` from the workspace's limits (owner and pending invitations take a seat). The team page turns inviting off when the plan has one seat or the seats are taken, and "add device" off when the plan's devices are paired; the server enforces seats, devices and roles (403 for too low a role). A role `<select>` goes back to the member's role when the update fails.
  - `AdminStore` holds the platform-admin data from `/api/admin/*` (customers, transactions, promo codes, subscription counts, 12 months of revenue, jobs) and the plans from the public `/api/plans`. `loadPlans()` runs in the app initializer; `load()` runs each time an admin page is entered (the `loadAdminData` `canActivateChild` guard in `admin.routes.ts`; it does not wait, the pages show "—" until `loaded`) and never throws. Every action re-reads what it may have moved (money, health figures, the customer's activity log). The data belongs to the signed-in user: another sign-in, or an assist session, empties it and drops late answers. Money dates (transactions, promo expiry, the finance page's "this month") use the Bangkok calendar like the server (`bangkokParts`); "today" elsewhere stays local. Plan limits in `AdminStore.plans` feed the plan cards (`featureLines()` in `plans.ts`: the four limits from `/api/plans`, advanced anti-ban on Pro and Agency only) and the admin pages.

  - Billing (Stripe; nothing about a card is stored or typed here). `BillingStore` (`core/data/billing.store.ts`) holds `GET /api/billing` (`info`: plan, cycle, status, `hasSubscription`, `renewsAt`, `cancelAtPeriodEnd`, the card Stripe has on file, `paymentsEnabled`, the signed-in customer's own `limits` and real `usage`) and `GET /api/billing/invoices` (charges, refunds and failed payments with Stripe's `receiptUrl`); `openPortal()` (`POST /api/billing/portal`) and `checkout(url)` leave the app through `RedirectService` (a service so specs can replace `window.location.assign`). `SessionStore.setPlan(plan, cycle, promoCode)` is `PUT /api/billing/plan`: it answers a Checkout address for a first paid plan (the page redirects to Stripe) or `null` when the plan changed on the server (a customer with a subscription: Stripe bills the difference at once, a declined card leaves the plan as it was; choosing Free schedules the cancellation for the end of the period; choosing the current plan again takes it back). **The plan in the UI only changes when the server says so**: the billing page (`/app/billing`) handles the return from Checkout (`?checkout=success&session_id=…` → `confirmCheckout`, `?checkout=cancel`) and the plan picked on the landing page (`?plan=`, passed through sign-up by `AuthPageComponent.welcome()`), and the webhook may apply the plan before or after that. Without a Stripe key the API answers `paymentsEnabled: false` and the page says online payment is off. A promo code is asked for only when a new subscription starts (it discounts the first invoice). The card and invoices are managed in Stripe's portal ("manage payment"). Admin: refunds and "retry payment" call Stripe through the API (`adminRefund`, `adminRefundLatest`, `adminRetryPayment`) and the finance page shows the amounts the API returns. Nothing here has been run against live Stripe.

  - `AdminStore.health` (`/api/admin/health`) feeds the admin overview's KPIs and system-health panel; `AdminStore.audit` (`/api/admin/audit?customerId=`) is the customer page's activity log and `globalAudit` (no customer) the plan and promo-code changes on the plans page; both are re-read after every action. Promo codes show as active, switched off or expired (past `expiresAt`), can be switched, and a new code is 3-30 letters or digits like the API's. The customer page compares what the API counts the way it counts it: accounts and posts (published in 24 h, never the failed ones) are owner-wide, devices and seats are per workspace.
  - Assist mode: "assist" on a customer calls `SessionStore.startAssist(id)`, which keeps the admin's token in `ap-assist` (`assistStorage`) and signs in with the customer's one-hour, read-only token. `AppLayoutComponent` shows the assist banner with "back to admin" (`endAssist()`); an expired assist token (401 in `authInterceptor`, or at `restore()`) also goes back to the admin. `WorkspaceStore` reloads whenever the signed-in user's id changes, so the switch reloads every workspace store.
  - `CampaignsStore` is the extension's own settings page on the web (`/app/campaigns`, "ตั้งค่าส่วนขยาย" / "Extension settings" (`api.extNav`; not called "ชุดโพสต์", which is step 1 of the posting flow), `features/campaigns`; an item of the sidebar's account group, apart from the posting flow, whose schedules hand their work to the extension without any of these settings (the page says so)): the settings JSON of one paired browser (`deviceId`, remembered in `ap-ext-device`) from `/devices/{id}/config`, normalized with the extension's own `migrateSettings`. Edits mutate that object in place through `change(fn)`, which bumps a tick (the `campaigns`/`campaign`/`global` computeds use `equal: () => false`) and saves 800 ms later with `baseRevision`; a 409 reloads the newer settings (`reloadedAt`). A save the API refuses (4xx other than 408/409/429) is not sent again by itself: it stays `error` with the API's reason (`saveError`) until the next edit; a busy or unreachable server is retried every 5 s. Viewers and assist mode are read-only (`CampaignActions.readOnly`); the Telegram bot token is hidden by the API below admin, so its field is disabled with a hint. `watch()` follows the device while the page is open: it subscribes to `DeviceEventsService` (below) and applies `device.state` (a `truncated` one refetches `/live`)/`device.log`/`device.log_cleared`/`device.online`/`device.config` events to `live` (a `device.config` with a newer revision reloads the settings when nothing is being edited), refetches `/live` whenever the stream (re)connects, and keeps a 60 s `/live` poll only as the fallback. Media goes to `/extension-images/{id}` as data URLs under new `uid()`s (`core/ext/media.ts` `processMedia` scales photos like the extension) and shows through object URLs. `command(cmd, args)` sends a button (start, stop, runNow, testPost, tgTest, tgFindChats) and waits for the `device.command` event with status `done` (a 5 s poll of `/commands/{id}` behind it) for `COMMAND_WAIT_MIN` (2) minutes, then reports `timeout`; the API keeps such a command for `COMMAND_LIFETIME_MIN` (10) minutes, so it may still run, and says `expired` after that; the texts say both; `CampaignActions` (provided by the page) adds the toasts and the viewer read-only rule.
  - `DeviceEventsService` (`core/data/device-events.service.ts`) is the workspace's live event stream: `GET /api/workspaces/{ws}/events/stream` (Server-Sent Events) read with `fetch` + `ReadableStream` so the bearer token travels in a header. One connection per workspace while anyone is subscribed (`subscribe(handler)`), reconnect with backoff and jitter, a 45 s stall detector (the server pings every 15 s), and `?after=<lastSeq>` on reconnect so the server first replays what was missed (the API sends `event: reconnect` when it rotates, shuts down or the backlog is too big). `connected`/`lastSeq`/`reconnects` are signals; `onResume(fn)` runs after every (re)connect so a store refetches what it shows. Stores keep a slow poll as the fallback. A 401, 403 or 404 on the stream stops it for good; the service ends its connection and listeners when its injector is destroyed. Event types and payloads: `DeviceEventType` in the backend. Import/export use the extension's `backup.js`, `zip.js` and `siri-import.js`.
  - **Still sample data:** the extension popup's activity list (labelled "sample"). `core/data/sample.ts` (the design's post generator and texts) feeds the landing-page preview only, so `seed.data.ts` ships in the landing page's chunk; platform names/icons (`core/data/platforms.ts`), month and weekday names (`core/i18n/calendar.ts`) and the design's plan defaults (`DESIGN_PLANS`, shown until `/api/plans` answers) are small constants outside it. The overview's figures include the sample accounts' posts of a new workspace.
- **Errors.** `core/http/problem-details.ts`: `problemOf(e)?.title` is the API's Thai message, `problemMessage(e)` the first field message else the title, `fieldErrors(e)` the messages by field; forms that send `QUIET` requests (invite, pairing, login) show them inline. A 403 on login means a suspended or banned account (`t().api.blocked`). `ago(t, date)` in `i18n.service.ts` formats last-seen times.
- **Derived views.** `DashboardStatsService` builds the KPIs, today's queue, the trend, accounts and recent errors for the overview; its pure helpers `kpisOf`/`queueRowsOf` also build the landing preview from sample posts. `core/data/plans.ts` builds the plan cards. `features/admin/AdminViewService` is provided in `admin.routes.ts` and holds the MRR, transaction rows, effective limits and job rows.
- **i18n.** `core/i18n/i18n.data.ts` is generated. Every leaf is a `[th, en]` pair, and `I18nService.t()` is a computed, typed dictionary for the current language. `core/i18n/i18n.fixes.ts` is a typed override layer (`Fixes<typeof AP_I18N>`: only existing leaves, both languages) deep-merged over the generated dictionary by `applyFixes()`; every corrected leaf carries a comment saying what the design got wrong (no 14-day trial, failure reasons that are TikTok/LINE samples, "rolls over to tomorrow", "same day" windows, reminders that nothing sends, a fixed version number, an "AI" writer that is only text templates and is called "post drafts (templates)"). Fix copy there, not in `i18n.data.ts`, so a re-import cannot undo it. The campaigns screen's strings (`api.ext`, ~35 kB) live in `i18n.ext.ts`, which registers itself (`registerExt`) when imported: every file that reads `t().api.ext` imports it, and the first bundle stays under its budget (only the nav label, `api.extNav`, is in `i18n.extra.ts`). Two more lazy packs follow the same pattern through `registerPack(name, part)`: `i18n.flow.ts` (`t().api.flow`: composer, collections, link sets, schedules, calendar, overview) and `i18n.engine.ts` (`t().api.engine`: test post, notifications, auto-reply, reports, anti-ban, backup, devices); import the pack in every file that reads it and append leaves under a comment block of your feature. Do not confuse `t().flow.*` (the design's stepper texts) with `t().api.flow.*` (the pack). Templates read `t().section.key` and fill `{placeholders}` with `fmt()`. Data that carries both languages (`L10n` pairs in the seed) is picked with `i18n.li()`. Use `format.ts` for dates (`fmtDate` uses the Buddhist year in Thai) and baht amounts.
- **Routing (`app.routes.ts`).**
  - `/`, `/login` and `/signup?plan=` sit under `PublicLayoutComponent`, guarded by `guestGuard`. `/connect-extension` and `/report/:token` (the public client report: anonymous snapshot, `?print=1` prints it; it shows only what the snapshot says: the brand as its heading, never the workspace name on a white-label report or beside a blank brand, a group as a link only when it has an http(s) address and as plain text otherwise) have no layout and no guard.
  - `/app/*` sits under `AppLayoutComponent`, guarded by `signedInGuard`.
  - `/app/admin/*` also requires `adminGuard`, and loads `features/admin/admin.routes.ts` (its `canActivateChild` guard reads the admin data on every page entered).
  - A route's `title` is the dotted path of its text in the dictionary (`'nav.overview'`); `DictionaryTitleStrategy` sets the tab title and follows the language switch. Every page is lazy loaded with `loadComponent`. `withComponentInputBinding()` feeds route data, query params and `:id` into `input()`s, for example `AuthPageComponent.mode`/`plan`/`returnUrl`, `CalendarPageComponent.day` and `CustomerDetailPageComponent.id`.
- **Styling.**
  - `src/styles/_tokens.scss` holds the color/space/radius/shadow tokens, with dark mode via `<html data-theme>` or the OS setting.
  - `_ds.scss` is the design-system CSS ported verbatim from the handoff bundle (`su-btn su-btn-sm su-btn-primary`, `su-input`, `su-select`, `su-check*`, `su-modal*`, `su-toast`, `su-empty*`).
  - `_ext.scss` holds the campaign editor's shared classes (`.ext-fs`, `.ext-in`, `.ext-grid`, `.ext-tabs`, `.ext-media`/`.ext-thumb`, `.ext-file`, `.ext-preview`).
  - `_app.scss` holds the repeated layout patterns: `.page`, `.page-head`, `.panel`, `.kpis/.kpi`, `.grid-2`/`.grid-2eq` (one column under 1024px), `.row`, `.status` + `.dot`, `.pico`, `.seg`, `.bar`, `.tbl/.th/.td`, `.callout`, `.tile`.
  - Components add only small local styles. Budgets: 6 kB warning / 10 kB error per component stylesheet. Icons are Phosphor font classes (`<i class="ph ph-...">`, plus `ph-fill`/`ph-bold`).
- **Tests.** Store and page specs use `src/app/testing/api-testing.ts`: `provideApiTesting()` sets up `HttpTestingController`, `signIn(http, { workspace, devices, posts, errors, user, collections, linkSets, schedules })` logs in and answers the workspace list and the loads of the stores that exist (also GET collections, master-posts (default: the posts of `collections`, each once; override with `masterPosts`), link-sets, schedules, notifications and auto-reply with empty defaults; a spec that touches a store which sits on `CollectionsStore`/`SchedulesStore` must answer or flush their lists before `http.verify()`) (`WORKSPACE` is the owner's workspace with limits), `settle()` lets promises and effects run. Inject `WorkspaceStore` before `signIn()` if nothing else does, or the list is never requested. `testing/fake-events.ts` (`FakeDeviceEvents`, provided for `DeviceEventsService`) lets a spec emit events instead of streaming. Specs that switch the language must clear `localStorage` afterwards (`ap-lang` leaks into other files); specs that depend on the time of day fake `Date`.
- **API contract.** After the backend's API changes, refresh `openapi.snapshot.json` (`curl localhost:5100/openapi/v1.json`) and run `npm run gen:api`; `api.service.ts` re-exports the schema types under `Api*` names.
- **Shared components** (`shared/components`): `app-modal` (put the buttons in `<div modal-footer>`), `app-rename-modal` and `app-confirm-modal` (one-field rename and delete confirmation, see the stores), `app-input-field`, `app-select-field` (`resetAfterChange` turns it into an action menu) and `app-checkbox`, all with `model()` two-way binding. `app-input-field` takes `maxlength`. Also `app-empty-state`, `app-plan-cards`, `app-cycle-switch`, `app-perm-note` (why a page's buttons are off), `app-toast-outlet` (driven by `NotificationService`), `app-flow-steps` / `app-next-step` (the four-step stepper and the simple-mode next-step card), `app-chip` and `app-feature-lock` (the plan lock banner).
- **Design source.** The handoff's `AutoPost Dashboard.dc.html` is the reference for layout and copy. The current handoff (BRD deliverables and approach, 2026-10-04) redesigned the flow as collections → link sets → schedules plus test post, notifications, auto-reply, reports and the advanced anti-ban settings; all of it is implemented against the real API. Where the prototype simulates (the post generator of the calendar, the test log, the comment feed, likes and comments, the AI writer, client report files) the real screens show real data, an honest empty state or a stored-only hint, and the dictionary corrections live in `i18n.fixes.ts`.
- **Naming.** Files use the 2016 style (`*.component.ts`), and `angular.json` schematics add the type suffix to class names.
- **Known limits (deliberate, not bugs to chase).**
  - A schedule keeps the browser's UTC offset as it was when the schedule was created (`utcOffsetMinutes`, sent by `utcOffsetMinutes()` in `core/flow/schedule-math`). Thailand has no daylight saving, so nothing moves there; in a time zone that changes its clocks, the schedule's posts drift by an hour until it is created again.
  - The link-set page's "example of the composed text" uses the settings (footer, hashtags, ...) of the FIRST collection (`LinkSetsStore.exampleSettings`), not those of the collection a schedule will pair with the set; it is only an example of how a group code is written into a post.

## Legacy app (`legacy/`)

```bash
cd legacy && npm install && npm run dev   # http://localhost:5173, proxies /api to VITE_BACKEND_URL (default http://localhost:8080)
```

If the legacy backend runs with `dotnet run`, it listens on 5080, so set `VITE_BACKEND_URL` to match. Every API call uses the cookie `fbap.auth` with `credentials: 'same-origin'`, so the page and the API must share an origin. `legacy/nginx.conf` proxies `/api/` to `http://backend:8080`.

- Pages: `index.html` + `web/admin.js` manage profiles and devices. `login.html` is the cookie login. `dashboard.html` + `dashboard.js` + `lib/*` are the extension's own settings page, reused as-is.
- `web/shim.js` loads before `dashboard.js` and fakes the `chrome` API on top of the legacy REST API:
  - The `settings` key maps to `/api/profiles/{id}/settings` with `baseRevision`; a 409 means the page must reload.
  - `img:<id>` keys map to `/api/profiles/{id}/images/*`.
  - `state` and `logs` come from polling `/api/devices/{id}/live`.
  - `sendMessage` becomes `POST /api/devices/{id}/commands` followed by polling `/api/commands/{id}`. Commands in `LOCAL_ONLY` are refused.

Most legacy files are copies from `siri_autopost_backend`, so keep them in sync:

|---|---|---|
